> 整理日期：2026-08-11  
> 适用环境：AIoT Vue / Falcon、ARMv7 glibc、800×254 横屏翻译笔

## 1. 本轮开发总结

这次开发完成了从“联网搜索”到“下载、转码、阅读、历史恢复”的完整链路，而不是只修改一个页面。

主要成果：

1. 将原漫画阅读器、在线搜索和文件管理功能适配到 X5 小程序运行时。
2. 针对翻译笔重新交叉编译 WebP 转 JPEG 原生模块，避免复用其他设备 ABI 不兼容的 `.so`。
3. 将 `libjsapi_webp.so` 嵌入 AMR，并接入 JavaScript 图片转换流程。
4. 修复 JM 请求头在不同 X5 固件上的兼容问题。
5. 绕过 X5 通用 HTTP 接口不能稳定写出下载文件的问题，改用 `custom.jm.downloadImage()`。
6. 修复图片动态 CDN 不可达导致的 `CURL error 28`，增加候选 CDN 回退和成功线路提升。
7. 将联网阅读记录归入历史页独立的“网络下载”分组。
8. 修复联网书库右上角长错误、下载路径和状态信息显示不全。
9. 每个高风险阶段均保留 Git 备份、构建 AMR、推送真机、截图和日志验证后再提交。

## 2. 原生 WebP 模块避坑

### 2.1 不要直接复制其他设备的 `.so`

即使两个设备都是 ARM，动态库也不一定通用。至少要确认：

- ARMv7 还是 AArch64；
- 硬浮点 ABI 是否一致；
- glibc、uClibc、musl 是否一致；
- 系统支持的 GLIBC 符号版本；
- QuickJS/Falcon 原生模块入口是否一致；
- 是否依赖目标系统不存在的动态库。

直接复制 `.so` 的典型后果：

- AMR 安装成功但模块加载失败；
- 页面白屏或黑屏；
- `could not load module`；
- `undefined symbol`；
- 调用原生函数时崩溃。

本项目使用目标设备匹配的工具链：

```text
arm-buildroot-linux-gnueabihf-gcc
```

构建入口：

```text
native/webp2jpg/build.sh
```

输出：

```text
ui/libs/libjsapi_webp.so
```

### 2.2 生成文件不等于构建正确

打包前至少检查：

```bash
arm-buildroot-linux-gnueabihf-readelf -h ui/libs/libjsapi_webp.so
arm-buildroot-linux-gnueabihf-readelf -d ui/libs/libjsapi_webp.so
arm-buildroot-linux-gnueabihf-readelf -Ws ui/libs/libjsapi_webp.so \
  | grep custom_init_jsapis
```

最低要求：

- 文件非空；
- `Machine` 为 ARM；
- 导出 `custom_init_jsapis`；
- 没有目标系统缺失的 `NEEDED` 库；
- 最终 AMR 中确实包含最新 `.so`。

验证要分三层：

1. 编译器和链接器成功；
2. ELF 架构、ABI、依赖和符号正确；
3. 真机运行时能导入并实际完成一次 WebP 转 JPEG。

### 2.3 模块和诊断程序不能机械共用链接参数

本轮同时生成：

```text
libjsapi_webp.so       # 小程序模块
webp2jpg-armv7         # 独立诊断程序
```

小程序模块可由运行时提供部分符号；独立程序必须自己满足线程、数学库和启动代码依赖。诊断程序缺少 `-pthread` 时会在链接阶段失败。

### 2.4 禁止构建失败后悄悄使用旧二进制

构建流程应强制：

1. 重建原生模块；
2. 校验输出文件；
3. 校验 ARM 架构；
4. 校验导出入口；
5. 任一步失败就停止打包。

最危险的不是构建直接失败，而是继续拿旧 `.so` 打包，让人误以为新代码已经进了真机。

## 3. X5 HTTP 与下载避坑

### 3.1 请求头字段名存在固件差异

部分固件读取：

```js
header: requestHeaders
```

另一些固件读取：

```js
headers: requestHeaders
```

只传一个字段时，普通 URL 可能正常，但 JM 这类依赖请求头的接口会出现搜索无结果、详情打不开或鉴权异常。

兼容写法：

```js
const requestHeaders = normalizeHeaders(options.headers);
const params = {
    url: options.url,
    method: options.method || 'GET',
    header: requestHeaders,
    headers: requestHeaders,
    data: options.data,
    timeout: timeout.native
};
```

### 3.2 HTTP 成功不代表文件写出成功

X5 通用 HTTP API 可能返回响应，却忽略 `filename` 或 `outPath`，形成假成功：

```text
HTTP 200
目标文件不存在或大小为 0
```

下载后必须检查：

- 状态码；
- 目标文件是否存在；
- 文件大小；
- 文件头是否符合预期；
- 转换后的 JPEG 是否真实生成。

本项目最终使用：

```js
custom.jm.downloadImage(url, outPath, timeoutSec, retryCount)
```

原生返回值也不能无条件相信：

```js
if (!result || result.ok !== true) {
    throw new Error(result && result.message
        ? result.message
        : 'native JM download failed');
}
```

### 3.3 超时单位必须在边界处转换

JavaScript 常用毫秒，CURL/原生接口可能使用秒。直接透传会导致 30 秒变成 30 毫秒或 30000 秒。

```js
const timeoutSec = Math.max(10, Math.ceil(timeoutMs / 1000));
```

## 4. `CURL error 28` 的正确排查方式

`CURL error 28` 只说明请求在规定时间内未完成，不代表单纯把 timeout 调大就能解决。

本轮真实根因是动态图片域名在翻译笔网络环境中不可达：

```text
不可用：https://cdn-msp.jmdanjonproxy.xyz
可用：https://cdn-msp2.jmdanjonproxy.vip
可用：https://cdn-msp.jmapiproxy3.cc
```

电脑浏览器能打开，不能证明翻译笔也能访问。两者可能存在不同的 DNS、TLS、SNI、IPv4/IPv6、CA 和运营商线路。

正确做法是对同一图片路径生成候选域名并按顺序尝试：

```js
for (const url of candidates) {
    try {
        await download(url);
        await verifyAndConvert();
        return success;
    } catch (error) {
        await cleanupPartialFiles();
    }
}
throw lastError;
```

注意：

- 只替换 host，保留路径和参数；
- 每次失败后删除残缺文件；
- 下载和转码都成功后，才算该线路成功；
- 成功 CDN 提升到候选列表首位，减少后续等待；
- JavaScript 已管理 CDN 时，应关闭原生层陈旧的 CDN 重试。

本项目最终调用：

```js
jm.downloadImage(url, outPath, timeoutSec, 0)
```

原则：**重试策略必须只有一个明确的所有者，避免 JavaScript 和原生层重复重试。**

## 5. 文件下载与图片转码避坑

推荐验证链路：

```text
下载原始文件
  → 检查存在
  → 检查大小
  → 检查 WebP 文件头
  → 转 JPEG
  → 检查 JPEG 存在和大小
  → 交给阅读器
```

失败后必须清理半成品。如果留下 0 字节或残缺文件，下一次仅按“文件存在”判断时会跳过重新下载，形成永久错误缓存。

应清理：

```text
原始 .webp
目标 .jpeg
历史遗留 .jpg
```

扩展名也不能代替格式识别。CDN 可能返回：

- `.jpg` URL，内容实际为 WebP；
- 无扩展名图片；
- 保存成 `.webp` 的 HTML 错误页；
- 依靠 `Content-Type` 声明格式的文件。

应结合 URL、响应头和文件魔数判断。

## 6. 800×254 小屏 UI 避坑

### 6.1 不要把它当缩小版浏览器网页

翻译笔可用高度很少，左侧导航栏还会占宽度。设计时必须控制：

- 页面总高度；
- 标题区和分组标题高度；
- 列表行高度；
- 实际滚动区域；
- 长路径、错误信息的换行；
- 标题和右侧状态之间的宽度竞争。

### 6.2 `<text>` 行为不能完全按浏览器 CSS 推断

X5/Falcon 对自动换行、`word-break`、`text-overflow`、动态宽度测量和混合插值的行为与浏览器不同。

本轮右上角状态最终采用手动切行：

```js
statusLines() {
    const value = String(this.message || '默认提示');
    const lines = [];
    for (let offset = 0; offset < value.length; offset += 42) {
        lines.push(value.slice(offset, offset + 42));
    }
    return lines.slice(0, 4);
}
```

```vue
<div class="network-status">
    <text v-for="(line, index) in statusLines"
        :key="index"
        class="network-status-line">{{ line }}</text>
</div>
```

这比依赖自动换行更稳定。

### 6.3 计数信息应靠近对应分组

历史页曾尝试在右上角同时显示本地数和网络数，但真机仍发生文字截断。最终取消顶部复合计数，在每个分组标题右侧显示自己的数量。

历史记录先整体倒序，再筛选分组，保证各组内部仍是最近阅读优先：

```js
displayItems() {
    return this.items.slice().reverse();
}
networkItems() {
    return this.displayItems.filter(item =>
        item.node && item.node.type === 'network'
    );
}
localItems() {
    return this.displayItems.filter(item =>
        item.node && item.node.type !== 'network'
    );
}
```

## 7. 真机调试避坑

### 7.1 页面参数不要想当然

本设备实际可用：

```bash
miniapp_cli start 8001749644971193 history
miniapp_cli start 8001749644971193 network
```

错误使用：

```bash
miniapp_cli start 8001749644971193 --history
```

会让设备把 `--history` 当成模块名，并出现：

```text
could not load module filename '--history.js'
```

即使 CLI 返回 `ret: 0`，也不代表页面成功渲染，必须继续看截图和日志。

### 7.2 黑色截图不一定是 CSS 问题

优先检查：

1. 页面参数是否正确；
2. 页面是否真正启动；
3. 屏幕是否熄灭；
4. 是否有模块加载异常；
5. 截图前是否等待了足够时间。

### 7.3 日志中的 ERROR 可能只是 `console.warn`

系统会把某些 JavaScript `console.warn` 记录成 ERROR。判断真实故障时应重点搜索：

```text
ReferenceError
TypeError
SyntaxError
could not load module
dlopen
undefined symbol
Segmentation fault
```

不要只按日志等级判断。

### 7.4 长文本必须用专门测试数据验证

默认提示很短，不能证明下载路径或 CURL 错误不会被截断。应临时准备长错误消息和网络历史记录做布局验证，截图确认后恢复正式数据，再重新构建最终包。

截图命令：

```powershell
& $adb shell '/usr/bin/miniapp_cli capture /tmp/page.png'
& $adb pull /tmp/page.png '.tmp-page.png'
```

## 8. 回滚、备份与 Git 避坑

1. 丢弃未提交修改；

## 9. Windows 构建环境避坑

### 9.1 PowerShell 管道可能破坏中文

包含中文的 here-string 通过管道传给 Python 时，如果控制台编码不一致，源码可能被写成 `????`。

规避方式：

- 优先使用 `Set-Content -Encoding utf8`；
- Python 修改脚本可使用 Unicode 转义；
- 修改后立即执行 `git diff`；
- 不要只看终端显示，要检查文件真实内容。

### 9.2 `EPERM lstat C:\Users\...` 可能是权限问题

Node 在受限环境中可能因为无法访问用户目录而失败。若同一命令此前正常，应先排查沙箱或权限，不要立刻修改项目代码和依赖。

### 9.3 `custom, webp` 缺失警告要结合原生模块判断

打包器静态扫描可能提示：

```text
未找到以下模块：custom, webp
```

对于由 `ui/libs` 提供的原生模块，这可能是预期警告，但必须确认：

- `.so` 已打入 AMR；
- JavaScript 导入名与原生注册名一致；
- 真机能加载并调用。

不能无条件忽略。

## 11. 故障排查速查表

| 现象 | 优先检查 | 不要先做什么 |
|---|---|---|
| 联网搜索无结果 | 请求头、API 返回体、真机日志 | 重写整个搜索页 |
| 点击开始阅读报错 | 章节 URL、下载文件、转码结果 | 只改 UI 提示 |
| `CURL error 28` | 真机域名可达性、DNS、CDN | 无限增加 timeout |
| HTTP 200 但无文件 | `outPath` 是否被忽略、文件大小 | 认为下载已成功 |
| WebP 转换失败 | ELF 架构、导出符号、输入文件头 | 复制其他设备 `.so` |
| 页面全黑 | 启动参数、模块日志、屏幕状态 | 立刻改 CSS |
| 右上角文字不全 | 真机 `<text>`、手动切行 | 只按浏览器推断 |
| 修复后旧问题复发 | 当前 HEAD、是否回滚过头 | 直接 `reset --hard` |
| 包安装成功但功能没变 | AMR 和 `.so` 是否最新 | 相信构建时间戳 |
| 日志大量 ERROR | 区分 `console.warn` 和异常 | 只按级别判断 |

## 12. 最重要的十条经验

1. 真机是唯一可信的运行环境。
2. 下载成功必须以本地文件为准，而不是 HTTP 返回为准。
3. `CURL error 28` 先查线路和 CDN，再改 timeout。
4. 原生 `.so` 必须针对目标 ABI 重编译并检查 ELF。
5. 重试策略只能有一个所有者。
6. 嵌入式 `<text>` 不能完全按浏览器 CSS 理解。
7. 高风险修改前先建备份分支。
8. 回滚前必须明确是回退工作区、一个提交还是指定版本。
9. 安装成功不等于页面运行成功，必须结合截图和日志。
10. 提交时精确选择文件，不能误删或误提交未跟踪的本地依赖。

遵循以上流程，可以显著降低“修好搜索却破坏下载、修好下载却破坏阅读、回滚时又丢掉已修功能”的概率。
